# 对官方 sta2eth 示例的改动说明

本工程基于 Espressif 官方示例 **`esp-idf/examples/ethernet/sta2eth`**（ESP-IDF v6.0.2）改造。
官方示例演示"WiFi STA ↔ 以太网"桥接的最小可运行模型；本项目在其上做了硬件适配、配网方案替换、
以及两项针对实际部署痛点的功能补丁。以下逐项说明**改了什么、为什么改、如何验证**。

---

## 1. 硬件适配（官方示例默认针对 ESP32-Ethernet-Kit，三个独立故障）

官方示例默认硬件是 ESP32-Ethernet-Kit（IP101 PHY），WT32-ETH01（LAN8720）上直接跑会有三个故障：

| # | 故障现象 | 根因 | 修复位置 |
|---|----------|------|----------|
| 1 | WiFi 连接报 `0xf00` 握手超时 | 官方 mbedtls 预设禁用 SHA1，而 WPA2 四步握手必需 HMAC-SHA1 | `mbedtls_preset_sta2eth.conf`：`CONFIG_MBEDTLS_SHA1_C=y` |
| 2 | 以太网初始化报 `reset timeout` | WT32-ETH01 的 LAN8720 复位/电源使能脚是 **GPIO16**，默认未驱动 | `sdkconfig.defaults`：`CONFIG_ETHERNET_PHY_RST_GPIO=16` |
| 3 | Link Up 但数据不通 | WT32-ETH01 由 LAN8720 的 25MHz 晶振倍频出 50MHz REF_CLK **输出**到 ESP32 的 GPIO0，时钟方向应为"输入" | `sdkconfig.defaults`：`CONFIG_ETHERNET_RMII_CLK_INPUT=y` + `CONFIG_ETHERNET_RMII_CLK_GPIO=0` |

其余 PHY 配置：`CONFIG_ETHERNET_PHY_LAN87XX=y`、`CONFIG_ETHERNET_PHY_ADDR=1`、`CONFIG_ETHERNET_PHY_INTERFACE_RMII=y`。

## 2. 配网方案：网页配网 → BLE 蓝牙配网

- **改动**：`main/provisioning.c` 的 scheme 由 httpd 换为 `network_prov_scheme_ble`；
  `sdkconfig.defaults` 打开 `CONFIG_EXAMPLE_WIFI_CONFIGURATION_PROVISIONING=y` 并启用 NimBLE；
  依赖组件 `espressif/network_provisioning` 声明在 `main/idf_component.yml`。
- **为什么**：现场设备没有网页配网需要的电脑/浏览器链路；蓝牙配网只需手机 App（ESP BLE Provisioning），
  且**长按 IO2 按键 2 秒**即可随时重新配网（保留官方的按键重配网机制，`CONFIG_EXAMPLE_RECONFIGURE_BUTTON=2`）。
- **验证**：长按按键 → 设备重启进入 `Starting provisioning` → 手机 App 扫描 `PROV_` 开头设备 →
  下发凭据 → `Provisioning successful` → 自动重启进入桥接。

## 3. 开启以太网混杂模式（关键配置，官方默认关闭）

- **改动**：`sdkconfig.defaults` 增加 `CONFIG_EXAMPLE_ETHERNET_USE_PROMISCUOUS=y`。
- **为什么**：官方示例的 MAC 槽位方案下，关闭混杂时 ESP32 的 EMAC 硬件过滤器**只接收"目的 MAC =
  网桥自己"的单播帧**，其余全部静默丢弃。后果是：桥后设备访问互联网（目的 MAC = 网关）一切正常，
  但**同一路由器的其他无线设备无法与桥后设备互通**（手机 ping 不通桥后电脑、平台 SSH 不进摄像头）。
  官方示例代码注释中其实写明了这一后果（`ethernet_iface.c` 顶部注释与 Kconfig 描述），但默认值仍为 n。
- **验证**：开启前：桥后设备 ping 无线终端 100% 丢包；开启后：全通。

## 4. ARP 学习补丁（本仓库核心原创改动）

- **位置**：`main/ethernet_iface.c` 的 `mac_spoof()`，ARP 处理分支。
- **官方行为**：网桥的 MAC 改写槽位 `eth_nic_mac` 只从**开机后第一个 DHCP DISCOVER** 学习，
  且一个槽位只服务一个设备。这意味着：**静态 IP 设备（不发 DHCP）永远学不到**，只能裸 MAC 透传；
  而裸 MAC 透传会把设备真实 MAC 发上空口，部分路由器会丢弃"载荷源 MAC ≠ 关联 STA MAC"的帧，导致不通。
- **补丁行为**：未学到 MAC 时，从**首个上行 ARP 帧**学习有线端 MAC，让静态 IP 设备与 DHCP 设备
  走完全相同的 NAT 路径（空口只出现网桥自己的 MAC），并打印日志：
  ```
  I (xxxxx) example_wired_ethernet: Wired client MAC learned from ARP: 0a:d1:23:99:60:4d
  ```
- **触发条件**：WiFi 已连接 + 以太网 Link Up + 设备发出 ARP（外部 ping 一下即可触发）。
- **验证**：静态 IP 摄像头（不发 DHCP）接网桥 → 外部 ping → 串口出现学习日志 → ping 通、telnet/RTMP 可用。

## 5. WiFi 发送丢包计数（可观测性补丁）

- **位置**：`main/sta2eth_main.c` 的 `wired_recv_callback()`。
- **官方行为**：`esp_wifi_internal_tx()` 失败只打 `ESP_LOGD`（默认日志级别下不可见）。
  以太网侧 100Mbps 线速灌包、无背压，空口拥塞时 WiFi 发送队列溢出**静默丢帧**，
  TCP 只能靠超时重传恢复，表现为 RTMP 推流延迟持续抬升——而现场完全看不到原因。
- **补丁行为**：失败时计数，首次及每 100 次打印 WARN：
  ```
  W (xxxxx) example_sta2wired: WiFi TX drop #100 (len=1518)
  ```
- **用途**：推流卡顿时看计数增长速度即可量化空口拥塞程度，指导降码率/换信道/双频分流。

## 6. 其他

- `connect_wifi()` 中增加 `esp_wifi_set_ps(WIFI_PS_NONE)`：关闭 WiFi 省电（modem sleep），
  避免下行流量在休眠窗口被丢弃；
- `app_main()` 开机打印**版本横幅**，用于在多份工程副本环境下确认设备实际运行的固件版本；
- 分区表 `CONFIG_PARTITION_TABLE_SINGLE_APP_LARGE=y`：开启 BT + 配网组件后固件较大，默认分区装不下。

## 7. 上游同步建议

若将来 Espressif 更新官方示例，重新移植时请保留：第 1 节的三项硬件配置、第 3/4/5 节三个补丁、
以及 `mbedtls_preset_sta2eth.conf` 的 SHA1 修正——它们分别对应硬件适配与本项目两项核心功能。
